# Benchmarks

Every performance claim this crate makes, with the measurement that supports it.

**Provenance.** Written by the PhotoshopAPI-rs port team; not an upstream png-spark document.
The crate was named `png-spark` when the baseline measurements were taken and was renamed to
`psd-png` on 2026-09-24. Package names in commands are the current ones. "Baseline" throughout
means png-spark 0.2.0, the code at `6d256fc`, which is what the A/B arm is built from.

**Companion.** [`design.md`](design.md) explains why the decoder is shaped this way. This
document measures the result.

## How to read these numbers

Two things are true of every table here, and both are properties of the measurement rather
than of the code.

**The machine throttles.** Sustained benchmarking on the measurement machine swings decode
time by more than 30% — one profiling run read the 4K fixture at 93.32 ms and the next at
69.35 ms for identical work. Any comparison drawn across two separate runs is therefore
meaningless, so:

- **Interleaved.** Arms alternate process-by-process, round by round. A round is one full
  pass over the fixture set per arm.
- **Best-of-N per round, minimum across rounds.** Each fixture's best decode time within a
  ~400 ms wall-clock budget, then the per-fixture minimum across 6 rounds. The best-of
  statistic is far more stable than the mean: running the baseline against *itself* for
  3 rounds produced byte-identical minima for every fixture, a delta of **+0.00%**.
- **One session.** Every number in this document comes from a single uninterrupted run.
- **Control arms.** Where a delta is small enough to matter, a third arm runs the same
  binary a second time in every round, so the day's noise floor is measured rather than
  assumed. The control column appears in the tables where it was used.

**Fixtures must come from a real match finder.** png-spark's own encoder emits only
zero-run, distance-1 matches, and all 180 reference-corpus images are smaller than the 32 KiB
match window. Neither can detect a reconstruction frontier whose lag is wrong, because
mid-stream reconstruction never engages. The large fixtures are therefore generated by
`tools/gen_large_fixtures.py`, which filters and compresses through CPython's zlib — a full
LZ77 match finder — and asserts each file exceeds the window. The largest is 36.9 MB
filtered. `tools/gen_testdata.py` supplies the 180-file small corpus.

Because of that, deltas below ~1% are still meaningful here, and the small-file table is
read at 100 ns granularity for exactly that reason.

| palette8_512 | 72.9 | 0.35 | 0.02 | 0.35 | 0.00 | 0.37 | −0.02 |
| rgb8_512 | 221.2 | 1.40 | 0.07 | 0.89 | 0.65 | 1.61 | −0.21 |
| rgba8_512 | 247.6 | 2.04 | 0.08 | 1.24 | 1.00 | 2.32 | −0.28 |

| rgba8_3840 | 5103.5 | 69.35 | 1.62 | 34.94 | 40.35 | 76.90 | −7.55 |

Inflate is **50–65%** of decode, unfilter **25–40%**, CRC **2–5%**, and the chunk walk,
allocation and compaction copies are small. The `parts` column exceeds `decode` because
unfilter is timed in isolation against a cold buffer; in situ it reads rows inflate has just
written. The negative `other` column is that isolation error, not a speedup.

The filter distribution in the port's own fixtures is dominated by `Paeth` — 91% of rows in
the 4K RGBA8 fixture, 85% at 512², 66–72% in the greyscale and 16-bit cases, and 100% `None`
for palette images.

## Fused reconstruction vs the baseline

Non-interlaced `decode` reversing filters in place as inflation passes, against the
two-pass baseline. Interleaved best-of-6, one session.

| fixture | filtered | baseline ms | fused ms | delta |
|---|---:|---:|---:|---:|
| rgba8_photo_3840x2400 | 36.9 MB | 52.27 | 47.60 | **−8.9%** |
| rgb8_photo_2048 | 12.6 MB | 18.03 | 17.11 | −5.1% |
| rgba16_gradient_1024 | 8.4 MB | 2.03 | 1.91 | −5.9% |
| rgba8_gradient_1024 | 4.2 MB | 5.55 | 5.19 | −6.5% |
| rgba8_mixed_1024 | 4.2 MB | 4.29 | 4.17 | −2.8% |
| rgba8_noise_1024 | 4.2 MB | 2.24 | 2.20 | −1.8% |
| rgba8_wide_4096x96 | 1.6 MB | 2.11 | 1.99 | −5.7% |
| rgba8_tall_64x4096 | 1.1 MB | 1.37 | 1.27 | −7.3% |
| gray8_gradient_1600 | 2.6 MB | 1.04 | 1.01 | −2.9% |

**9/9 faster.** The headline fixture is the port's dominant class — RGBA8 4K is the shape
smart-object rasters arrive in, and 13 of 13 PNGs in the port's corpus are RGBA8
non-interlaced. The noise fixture's −1.8% is the conservative floor: literals dominate, so
the frontier's per-batch check is at its densest while the second pass it eliminates was at
its cheapest. Both shape extremes win — 16 KiB rows × 96 and 257-byte rows × 4096 — so the
gain is not an artefact of one row size.

## Small files: equal within the measurement floor

Ten fixtures bracketing the 32 KiB window and below. 5 interleaved rounds, best-of-3000 per
fixture, in nanoseconds.

| fixture | baseline ns | fused ns | delta |
|---|---:|---:|---:|
| rgba8_small_64x184 (47 KB, over window — fused) | 58 500 | 58 400 | −0.2% |
| rgba8_small_64x92 (24 KB, under window — legacy path) | 30 400 | 30 800 | +1.3% |
| ct2_d8_i0_63x40 | 4 600 | 4 600 | +0.0% |
| ct2_d8_i0_32x17 | 1 600 | 1 600 | +0.0% |
| ct0_d1_i0_63x40 | 500 | 600 | +20% (one 100 ns bucket) |
| five ≤1 px–9 px corpus files | 300–1 800 | identical | +0.0% |

Below the window gate the decoder runs the **byte-identical two-pass path**, so the residual
deltas at this scale are benchmark layout, not the feature — the +20% row is +100 ns on a
500 ns decode, one measurement bucket, on a path with no frontier code in it. The 47 KB file
just over the threshold nets to −0.2%: fusion's savings and its polling cost cancel at
exactly the size where the gate belongs.

## Streaming vs whole-image

`decode_to` against `decode`, like-for-like: the sink copies every row into a presized
buffer, so both arms deliver identical pixels. Interleaved in one process, best-of-6.

| fixture | decode ms | decode_to ms | delta |
|---|---:|---:|---:|
| rgba8_photo_3840x2400 (36.9 MB) | 47.78 | 49.45 | +3.5% |
| rgb8_photo_2048 | 17.30 | 17.53 | +1.3% |
| rgba8_gradient_1024 | 5.21 | 5.34 | +2.5% |
| rgba8_mixed_1024 | 4.16 | 4.37 | +5.0% |
| rgba8_noise_1024 | 2.18 | 2.23 | +2.3% |
| rgba8_wide_4096x96 | 2.00 | 2.08 | +4.0% |
| rgba8_tall_64x4096 | 1.27 | 1.28 | +0.8% |
| gray8_gradient_1600 | 1.01 | 1.06 | +5.0% |
| rgba16_gradient_1024 | 1.83 | 2.32 | +26.8% |

Streaming costs **≤5%** on every class except 16-bit gradients: +27%, which is 0.5 ms
absolute on an 8 MB image, where per-row emission and slide traffic show most because
inflate itself is nearly free.

Against a **discarding** sink the comparison inverts — `decode_to` is faster than `decode`
outright, because it never allocates or first-touches the whole-image buffer. For the port,
whose consumer de-interleaves rows into planar channels, that allocation leaves the pipeline
entirely.

The size ceiling behaves as designed: a 16384×16384 RGBA image (~1.07 GB filtered) is
refused by `decode` under the 512 MiB default and streams through `decode_to` in a ~300 KB
stage (`tools/gen_bomb_fixture.py`, `tests/streaming_decode.rs`).

## Fused conversion vs png-spark 0.2.0

The question the port actually asks: what is the fastest route to the pixels it consumes.
Both arms deliver the same thing — every pixel as 8-bit RGBA in a buffer the caller keeps —
and each takes the best route its version has.

| arm | route |
|---|---|
| png-spark 0.2.0 | `decode` into the file's own layout, then `to_rgba8` as a second pass |
| this crate | `decode_to_rgba8`, converting each row as it is reconstructed |

`bench/src/bin/convert_bench.rs`, one copy per worktree and identical apart from the route.
Process-level interleaving, per-fixture minimum across 6 rounds, arm order alternated per
round, and a control arm — this crate's own binary run a second time every round — to
measure the day's noise.

| fixture | baseline ms | fused ms | delta | control noise |
|---|---:|---:|---:|---:|
| rgba8_photo_3840x2400 (36.9 MB) | 60.66 | 50.25 | **−17.2%** | +0.5% |
| rgba8_tall_64x4096 | 1.57 | 1.30 | −17.2% | +0.0% |
| rgba8_noise_1024 | 2.97 | 2.24 | −24.6% | +2.2% |
| rgba8_gradient_1024 | 6.39 | 5.45 | −14.7% | +0.0% |
| rgba8_mixed_1024 | 5.08 | 4.51 | −11.2% | −0.4% |
| rgba8_wide_4096x96 | 2.43 | 2.14 | −11.9% | +0.0% |
| rgb8_photo_2048 | 22.05 | 20.76 | −5.9% | −0.5% |
| rgba16_gradient_1024 | 3.31 | 2.48 | **−25.1%** | +0.4% |
| gray8_gradient_1600 | 3.67 | 3.50 | −4.6% | +0.6% |

**9/9 faster, mean −14.7%.** Every delta clears its own control noise, including the 4.6% on
the grey fixture. The control's 2.2% outlier is the noise image, where a fixed absolute
jitter is proportionally largest; the other eight sit at or below 0.6%.

### What the conversion itself costs

The same session, this crate's three arms (minimum across 6 rounds), isolating the two
overheads that remain.

| fixture | decode | stream (native rows) | rgba8 (converted) | conversion cost |
|---|---:|---:|---:|---:|
| rgba8_photo_3840x2400 | 47.46 | 49.24 | 49.48 | +0.5% |
| rgba8_gradient_1024 | 5.24 | 5.41 | 5.41 | +0.0% |
| rgba8_mixed_1024 | 4.20 | 4.45 | 4.41 | −0.9% |
| rgba8_noise_1024 | 2.19 | 2.22 | 2.24 | +0.9% |
| rgba8_wide_4096x96 | 2.00 | 2.07 | 2.08 | +0.5% |
| rgba8_tall_64x4096 | 1.30 | 1.29 | 1.31 | +1.6% |
| rgba16_gradient_1024 | 1.87 | 2.36 | 2.47 | +4.7% |
| rgb8_photo_2048 | 17.09 | 17.52 | 20.72 | +18.3% |
| gray8_gradient_1600 | 1.00 | 1.07 | 3.45 | +222% |

- **For an 8-bit RGBA source the conversion is free.** The ≤1.6% measured here was the row
  copy into a scratch buffer, which a later change removed: a source already in the
  requested layout now hands rows to the sink untouched. The port's dominant class pays
  nothing.
- **The two expensive cases are paid in output bytes, not arithmetic.** An RGB source asked
  for RGBA writes four bytes per pixel where the file had three (+18%); a grey source writes
  four where the file had one (+222%). Both are inherent to the deliverable, and this crate
  still wins both against 0.2.0, which pays the same volume *and* a second pass over it. A
  consumer that does not need alpha can ask for `decode_to_rgb8` and take a quarter off the
  grey case.
- **16-bit from an 8-bit source** (+4.7%) is the only case doing real per-sample work, and
  is still four times cheaper than the two-pass route it replaces (−25.1% overall).

## SIMD `Paeth`

### Why this filter, and why it turned out to matter

`bench/src/bin/stage_split.rs` times inflation alone against a whole decode on the same
bytes and counts the filter bytes in between.

| fixture | filter mix (rows) | inflate | decode | ratio | unfilter (cold) |
|---|---|---:|---:|---:|---:|
| rgba8_photo_3840x2400 | **2400 Paeth** | 18.0 ms | 48.6 ms | 2.70x | 44.5 ms |
| rgb8_photo_2048 | **2048 Paeth** | 6.6 ms | 17.2 ms | 2.61x | 14.5 ms |
| rgba8_gradient_1024 | **1024 Paeth** | 1.8 ms | 5.2 ms | 2.85x | 5.0 ms |
| rgba8_mixed_1024 | mixed, 438 Paeth | 3.2 ms | 4.2 ms | 1.33x | 2.6 ms |
| rgba8_noise_1024 | 1024 Up | 2.0 ms | 2.2 ms | 1.08x | 0.3 ms |
| rgba16_gradient_1024 | 1024 Up | 3.8 ms | 1.9 ms | 0.51x | 0.5 ms |

Reconstruction is **not** hidden inside inflation. The frontier runs it inline, between
decode-loop iterations, so the cost is exposed rather than absorbed, and the only thing the
fusion saves against the old two-pass decoder is cache locality — 44.5 ms cold against
roughly 30 ms hot on the 4K fixture, which is the −8.9% above.

Within reconstruction, everything is `Paeth`: at 790 MB/s against inflation's ~2000 MB/s it
is the entire cost wherever it appears, and on `Up`/`Sub` images it is invisible. That is why
the kernel targets `Paeth` and not the other filters, and why any gain here is
data-dependent rather than uniform.

### Results

A scalar build (`--features scalar-override` with `PSD_PNG_FORCE_SCALAR=1`) against a
default build, `decode_to_rgba8`, interleaved per round with a control arm running the
default a second time, 6 rounds, per-fixture minimum.

| fixture | scalar ms | SIMD ms | delta | control noise |
|---|---:|---:|---:|---:|
| rgba8_photo_3840x2400 (35 MiB, all Paeth) | 50.30 | 39.03 | **−22.4%** | +2.3% |
| rgba8_tall_64x4096 (all Paeth) | 1.30 | 1.05 | −19.2% | +0.0% |
| rgba8_wide_4096x96 (all Paeth) | 2.09 | 1.67 | −20.1% | −1.2% |
| rgba8_gradient_1024 (all Paeth) | 5.39 | 4.27 | −20.8% | +0.7% |
| rgba8_mixed_1024 | 4.38 | 3.89 | −11.2% | +0.5% |
| rgb8_photo_2048 (3-byte stride) | 20.83 | 18.67 | −10.4% | +0.1% |
| rgba8_noise_1024 (all Up) | 2.26 | 2.22 | −1.8% | +0.9% |
| rgba16_gradient_1024 (all Up) | 2.50 | 2.44 | −2.4% | +0.0% |
| gray8_gradient_1600 (all Sub) | 3.54 | 3.54 | +0.0% | +0.0% |

**Mean −12.0%**, with the three `Up`/`Sub` fixtures sitting inside the control noise — which
is the shape the filter mix predicts, and is the check that the kernel is not merely doing
something on images that have no `Paeth` to do.

On the port's own twelve PNGs — mixed, roughly 200–350 `Paeth` rows of 512 to 1 MiB each —
the same measurement gives **−8.1% to −15.9%, mean −12.4%**, with control noise at or below
2.2% on every file.

For scale: that 4K fixture's `decode_to_rgba8` was 49.48 ms before the kernel and 39.03 ms
after, so the kernel is worth more on that file than fused reconstruction and fused
conversion combined.

## Where the remaining time is

The plumbing is no longer where the time is. For the port's class, streaming costs 3–4%
over a whole-image decode and the fused conversion costs under 2% on top of that, so what is
left is inflation and filter reversal — the serial Huffman loop and the serial per-row
reversal, which is what the whole design was built to overlap. Going further means attacking
those directly.

There is no 2× hiding in this design, and it is worth being plain about why. Decode is
DEFLATE-bound: the inflate core is fast, and the state of the art beyond it is years of C
micro-work rather than a patch. The wins here came from *not doing work twice* (fusion), *not
allocating the whole image* (streaming), *not copying between layouts* (fused conversion),
and *not running the scalar predictor* (the SIMD kernel) — not from a faster Huffman decoder.

## Correctness gates

The performance work is worthless if the bytes are wrong, so each of these is a gate, not a
suggestion. All green as of the final commit.

| gate | result |
|---|---|
| `cargo test` (workspace, 16 test targets) | all green |
| reference corpus, 180 files (`tools/gen_testdata.py`) | byte-exact, 180/180 |
| fused vs two-pass path (`tests/fused_reconstruction.rs`, 9 zlib fixtures ≤ 36.9 MB) | byte-exact, 9/9 |
| frontier unit tests (filters × strides × Paeth-run alignments, fired-mid-inflation, invalid-filter freeze) | 10/10 |
| streaming parity: rows vs `decode()` on 9 large fixtures + 24 corpus files, interlaced included | byte-exact |
| segmented vs one-shot inflate over 224 reference zlib vectors, stage barely larger than the window | byte-exact |
| `cargo clippy --all-targets` | clean |
| `cargo fmt --all --check` | clean |
| Miri over the filter tests (nightly) | green |

`cargo test` is a two-arm gate: `PSD_PNG_FORCE_SCALAR=1 cargo test --features scalar-override`
runs the whole suite against the scalar paths. Both arms must be green — that is what holds
the SIMD kernel and the scalar wavefront to the same bytes.

**Not run locally:** the three `cargo fuzz` targets. The inflate core was restructured around
a `SEGMENTED` const generic whose `false` instantiation is *intended* to compile to the old
loop, and fuzzing is how that intention gets verified. CI runs them weekly.

**Miri coverage is partial.** Green for the filter and frontier layers. The inflate core's
segmented variant is not Miri-covered on a Windows host — Miri cannot enumerate the corpus
directories there, and the filesystem-free inline case exceeds a practical interpreter
budget — so a Linux Miri run in CI covers it instead.

### What the gates caught

Recorded because each one was invisible to the suite that existed before it.

- The tail drain initially kept the lag precondition, which is unsatisfiable below one match
  window. Every small image would have been left unreconstructed.
- When the shared inflate block moved, the Adam7 arm was left uninflated: 87 corpus failures.
- `Checks::Full` verified Adler-32 over a buffer the fused path had already partly rewritten,
  rejecting every valid non-interlaced image past the match window — in both `decode` and
  `decode_to`, and invisible because the default is `Checks::Crc` and the fuzz corpus is all
  sub-window images. Fixed by hashing inside the progress hook, ahead of each reconstruction.
- The SIMD kernel's parity tests caught two real bugs: `packus` against itself interleaves
  the lanes, so the third channel of every pixel was written as a duplicate of the second;
  and the loaded vector holds four adjacent bytes rather than four lanes, so the load had to
  be widened before the 16-bit arithmetic. A tie-break mutation that swaps the `a`/`b`
  preference fails three tests, so that property is genuinely pinned rather than incidentally
  covered.
- `decode_to` could panic ("budget must leave OUTPUT_SLACK") on valid non-interlaced images
  with rows narrower than about 130 bytes — greyscale under 128 pixels wide, RGBA under 32 —
  when a DEFLATE match ended exactly where a segment paused. The frontier trailed the cursor
  by up to a whole match, so the stage slide kept more than its headroom. Found by a random
  search over narrow images, roughly once in 500.
- A row's byte size was computed in `usize` from a bit count that can be wider than `usize`
  even when the byte count is not, so a header naming a very wide image overflowed that
  multiplication: debug builds aborted on the untrusted header, release builds wrapped to a
  smaller size and understated the buffers and the ceiling they are checked against.

## Reproducing

```sh
python3 tools/gen_testdata.py       # 180-file reference corpus
python3 tools/gen_large_fixtures.py # the large fixtures used above
python3 tools/gen_bomb_fixture.py   # the size-ceiling fixture

cargo test
cargo test --features scalar-override      # with PSD_PNG_FORCE_SCALAR=1 in the environment

cargo run --release -p psd-png-bench --bin profile -- tmp/large
cargo run --release -p psd-png-bench --bin stream_decode -- tmp/large
cargo run --release -p psd-png-bench --bin stage_split -- tmp/large
cargo run --release -p psd-png-bench --bin convert_bench -- tmp/large
python3 bench/tools/filters.py tmp/large
```

The interleaved A/B harness that drives the two-arm tables is not part of this repository,
so the arm-alternation and per-round minimum have to be reproduced by whichever harness you
build. What the numbers *do* depend on staying reachable is the baseline arm: a `git
worktree` of `6d256fc`, which is the code the "baseline" columns measure.
